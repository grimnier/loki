# loki — the front end for the R1 runtime

**Before changing anything:** read this file, run the replay once to see the interface, then stop and report to
the owner (the owner) what you understand of the design and what you would change. He wants to give his points
before any work starts.

**Not negotiable.** These are the owner's rules, and they are pinned by tests. Do not trade them away for a
feature, and if a change would touch one, say so before it goes in.

1. **The hood is a TV.** It is on while the model thinks: the last few lines of the thought show under a dim
   status line. When the thought ends it is off: the hood drops and the chain of thought is *gone* from the
   screen — not folded, not greyed, not reachable, gone. A dim `thought for Ns` line is all that remains.
   The text itself is kept (in the log entry and the conversation file); it is simply not drawn. What a tool
   returned is a different thing and may fold open under its `→` line in the window.
2. **Two tones, one box.** Normal text and dim text, nothing else. The input box is the only thing drawn.
   No bands, borders, panels, shades or badges; no third colour.
3. **Nothing on screen that is not doing something.** While loading, nothing. While idle, the conversation
   and the box. A line appears when it has something to say and leaves when it is done.
4. **Smooth.** Text flows at a steady pace; what moves, moves on a curve; nothing jumps, flickers or reflows
   while you watch.

This folder is the client. The DeepSeek-R1 671B runtime (`src/server_core_async.cpp`, generated by
`make_server_core_async.py` plus the `patch_*.py` chain in the repo root) runs on one Windows laptop with an
RTX 4050 and the weights on its NVMe. Weights, the geometry-memory files (`ptx_trees/`), captures and results
are not in git; nothing here needs them to work on the interface. Everything is standard-library Python 3 and
plain HTML/CSS/JS — no dependencies, the terminal starts in about 200 ms.

```
loki/
  chat.py        the terminal client; also the turn logic, settings, conversations and the tool loop
  term.py        the terminal under it: glyphs, display widths, wrapping, a diff-drawn screen, keys and the wheel, easing
  app.py         the same client as a window: a local server, the page, Edge/Chrome as an app window
  web/           the page (index.html, app.css, app.js)
  tools/         the tool belt: web, browser, system, local
  studio/        the queue runner and the stub agent for the 4K picture / video model
  tests.py       headless tests over the replay
bin/             launchers: loki, loki-app (.cmd for Windows)
```

## Running it

```bash
loki                                   # bin/loki (.cmd on Windows): the terminal, with the real engine
loki --sandbox                         # memory for this conversation only (see Memory below)
loki-app                               # the window
python3 loki/chat.py --replay 4        # the terminal against three turns captured from the real model, at 4 tokens/s
python3 loki/app.py --replay 12 --no-open   # the window the same way; open http://127.0.0.1:8765/
python3 loki/tests.py                  # eleven headless tests, about two minutes
```

Settings persist in `chat_settings.json` in the repo root (ignored by git). Transcripts go to
`results/chat/<date>.md`, conversations to `results/conversations/`, tool runs to `results/tools/`.

## The design

The owner's brief: simple, nothing flashy, like working from a blank terminal; nothing shown while things
load; the box you type in sits at the bottom and grows as you type; the conversation fills upward from it;
the model's thought shows in a few lines under a hood that can be opened; the thought should flow smoothly as
it arrives. Two tones of text, normal and dim. The only drawn thing is the input box.

The real model runs at about 1 token/s on a fresh question (2.5–4 on paths it has seen), so a thought takes a
minute or two and the timer is often the only thing moving. The context is 256 positions by default; a turn
is budgeted as think + answer tokens and the client starts a fresh context, carrying the last exchange when
it fits, once a turn would not fit.

## The terminal (`chat.py`)

Bottom up: the input box (rounded border, word-wrapped, one row per line); the hood while thinking — a dim
`thinking · 1m 12s` line and the last `bars` lines of thought (4 by default), nothing drawn around them,
paragraph gaps skipped so every row is text; the conversation above. Text arriving under the hood fills each
row left to right and only moves down when a word completes (`flow()`), so nothing reflows while you watch.
When the thought closes the hood drops over it in three frames and leaves a dim `thought for Ns` line; the
answer streams above the box, then a dim stats line.

**Motion.** The engine hands over tokens in bursts, one pass every second or two; the screen releases
characters at the measured arrival rate instead (catching up when it falls behind), so the thought flows at a
steady pace. The hood drops over a finished thought on an easing curve (260 ms) and opens or closes on Tab
the same way (200 ms); the `›` mark pulses softly while the model works, so a slow pass never looks like a
hang. A frame clock runs keys, the engine, the smoothing and one repaint thirty times a second, and only the
rows that changed are sent to the terminal, so it holds up over SSH and in tmux. All of that is `term.py`
with `chat.py`'s `smooth()`.

**Pace, truthfully.** The engine writes what each pass was to stderr (`[live] … tok/s`, `pass k: D drafted, A
accepted`, `[geometry] N tokens from stored walk`; `fixtures/` on `main` has the real thing, and the three
shapes the client reads were checked against it). The client keeps that stream
(`results/server_core/chat_engine.log`, as before) and reads it: the hood's status line carries the running
rate and the kind of the last pass — `thinking · 1m 12s · 1.2 tok/s · drafted`, or `· stored` for a stretch
emitted from memory with no pass, `· cold` for a pass with no draft at all — and the title carries the same
while the answer streams. In chat mode the engine writes no per-turn summary (its `geometry runs:` and
`family drafts:` lines come once, at exit), so the client adds the turn up from the pass lines and leaves one
dim line under it: `0.8 tok/s · 228 passes · 13 tokens from drafts · 32 from stored runs · 215 cold`, with
the zero parts left out. The replay feeds the same lines synthetically so it can be seen without the engine.

**Typing.** `/` opens the palette: the commands that match what you have typed, with one-line descriptions;
Up/Down pick, Tab completes, Enter takes the selected one. Up on an empty box recalls what you sent, older
each press, Down comes back; inside a draft that spans rows, Up/Down move between its rows. Ctrl-←/→ jump by
word, Ctrl-K kills to the end of the line, Ctrl-U to the start, Ctrl-W the word before the caret, Ctrl-J
breaks a line (pasted newlines stay inside one message). The draft is saved as you type and is back after a
restart. Enter while the model is answering queues the message (a dim `queued ·` line above the box); it
goes the moment the turn ends; Esc on an empty box clears the queue. CJK, emoji and combining marks take the
columns they take, so the box border stays put.

**Files with a message.** `@notes.md` (or `@"a path with spaces"`) anywhere in a message brings that file's
text along with it, cut at `attach_cap` characters (6000); a dim `attached notes.md · 1,204 chars` line says
what went. Tab completes the path. What is carried into the next context is the message as you typed it, not
the file.

**When it is done.** The title reads `loki · done` for a few seconds after an answer lands, and the terminal
bell rings when the answer took `bell_after` seconds or more (15; `"bell": false` turns it off) — the case
where you walked away. The window sends a system notification when it is not in front (it asks once, on
the first send).

**If the engine stops.** A dim `engine stopped · /restart starts it again · Tab shows its log` line, with the
last thirty lines of `results/server_core/chat_engine.log` folded under it; `/restart` starts the engine again
and the conversation continues from its last exchange. The window shows the same line with a restart link.

**Keys.** Enter sends; Tab opens the hood over the screen — the whole thought, scrollable with
Up/Down/PgUp/PgDn and the wheel, following the newest line until you scroll up, a small dim `●` in the right
margin when there is more than fits — and closes it; Tab when idle does nothing (a finished thought stays off);
Esc stops a running turn, or clears the box; Ctrl-C stops a turn, or quits on a second press within two
seconds; PgUp/PgDn and the mouse wheel scroll the conversation (Up/Down too, when the box holds a single line
of text), with a hairline on the right edge showing where you are while you scroll and `↓ N more` on the
last row when you have scrolled up during a stream; `y` / `n` / `a` answer a tool that asks.

**Commands.** `/new` next conversation · `/chats` the last twelve · `/find WORDS` search every conversation
(a snippet each; `/open N` picks from the list) · `/open N` continue one · `/restart` the engine · `/again` ask
the last message again · `/edit [N]` edit the Nth-last message and continue from it (both keep the old tail
as a branch in the conversation file) · `/fast` `/deep` presets (`"presets"` in the settings: fast is ctx
128, think 60, answer 80, tools off; deep is ctx 2048, unlimited, tools on; a context change restarts the
engine) · `/think N` `/answer N` token budgets (0 = unlimited) · `/bars N` lines under the hood · `/stats`
the speed line · `/ctx [N]` context · `/sandbox [on|off]` `/memory` memory mode · `/tools` `/tool NAME
allow|ask|off` `/hops N` `/rules` `/cap N` the tool belt · `/copy` the last answer to the clipboard ·
`/queue [clear]` · `/quit` · `/help`.

Also there: the terminal title carries `loki · thinking 1m 12s`; `loading the model · 42s` sits above the box
until the engine is up; a dim `context full · fresh start · carrying the last exchange` line says when a turn
forced a fresh context. Terminals that cannot draw the rounded corners and marks (conhost with a raster font,
non-UTF-8 shells) get plain ASCII rules automatically; `--ascii` or `LOKI_ASCII=1` forces it, `--no-mouse` or
`"mouse": false` leaves the wheel alone. Piped stdin falls back to a plain line mode (no hood, no tools).

**Memory modes.** *shared* (default) loads the model's accumulated geometry and route memory from every past
conversation and saves back at exit; *sandbox* (`/sandbox`, or `loki --sandbox`) gives the engine fresh
scratch memory files, so reuse still works inside the conversation but nothing from earlier chats is loaded
and nothing is kept; the scratch files are deleted at exit. Switching restarts the engine and starts a new
conversation.

## The window (`app.py`, `web/`)

`python3 loki/app.py` starts a server on 127.0.0.1:8765, opens the page as a chromeless app window (Edge or
Chrome `--app=`, else a browser tab) and streams the conversation to it. `Session` is `TUI` with the screen
replaced by a state stream, so the turn logic, commands, settings, conversations and tools are shared with
the terminal, not duplicated. Same look: dark backdrop, two tones, one rounded composer, the same hood (click
the status line or Tab to open the whole thought), `thought for Ns` and `→ tool` lines that fold open, answers
rendered with the little markdown the model uses, `copy` on hover, bare URLs as links. The top of the
conversation fades out instead of hitting the edge.

**Keys.** Enter sends, or queues the message while the model answers (dim `queued ·` lines above the box;
Esc on an empty box clears them); Shift-Enter breaks a line; `/` opens the palette (Up/Down pick, Tab
completes, Enter takes the selection); Up in an empty box recalls what you sent, older each press; Esc stops
or clears; typing anywhere lands in the box; Tab opens the thought; Ctrl-B the conversations; Ctrl-. toggles
compact mode; Ctrl-, opens the knobs from anywhere (compact mode has no rail). Hover a message of yours for
`edit` (back into the box, the old tail kept as a branch) and `again`. The window title carries the timer; a
`↓` appears when you have scrolled up during a stream; the hint line under the box says `loading the model ·
Ns` or `reconnecting` when that is the state, and otherwise leaves once a conversation exists. New lines in
the conversation ease in; keyboard focus shows a ring, a click never does. The chats view has a find
box that searches every conversation and shows a snippet each; rows say how many branches a conversation
keeps.

**The rail**: chat · studio · chats · `+` new · knobs · a context meter. **Knobs** are the settings — think,
answer, hood lines, context, stats, window mode, tools on/off/auto, hops, result cap, the belt (click a tool
to cycle allow → ask → off) and the remembered rules.

**Compact mode.** Under 880 × 560 (or `window: compact`, or Ctrl-.) the rail, hint and meter leave and the
conversation has the whole window. The composer is a visor hinged on the top edge: a dim pill is all that
shows; it swings down when you type, hover the top edge, press `/` or click the pill, and back up when you
send or press Esc. Conversations are a drawer hinged on the left edge: hover the edge, click the pill, or
Ctrl-B; picking one swings it back. Grow the window and the full layout returns.

**Resume.** A reload comes back to the same view, scroll and open thought when it is the same conversation.

## Conversations

Every conversation is a file, `results/conversations/<id>.json` (title from the first message, the log, the
history), written after every turn. `/new` keeps the old one and starts another; `/open N` (or a click in
the window) brings one back and continues it: its log returns and the next message goes into a fresh context
carrying that conversation's last exchange. The daily markdown transcripts are still written as before.

## The tool belt (`tools/`)

The model only emits text, so a tool is something the client does on its behalf: the answer ends in a call,
the client runs it, shows the model the result as the next user turn, and the model carries on — one call per
turn, up to `hops` turns (4). `chat.py` owns the loop (`finish` → `run_tool` → `continue_turn`); `app.py` gets
it for free. Nothing in `tools/` touches the engine.

- **Format.** The tool list opens every fresh context (`tools.preamble`, about 1100 tokens, so `"tools":
  "auto"` only offers it when `ctx` is 2048 or more; `/tools on|off|auto`). A call is
  `<tool>{"name": "search", "args": {"q": "…"}}</tool>` on the last line of the answer (a ```json block with
  name/args is accepted). The result comes back as `<result name="search">…</result>`, cut at `tool_cap`
  characters (4000; `/cap N`, or `tool_caps` per tool). When the model closes a call the client stops the
  engine at once, so a tool turn costs the call and nothing after it. A tool that hangs is abandoned after
  `tool_timeout` seconds (90; `tool_timeouts` per tool).
- **Policy.** Each tool is `allow`, `ask` (the owner confirms: `y` / `n` / `a` in the terminal, allow / always
  / deny in the window) or `off`. Defaults: write, shell, python, kill, http, download and type ask; the rest
  run. `a` / always remembers the answer for that command (`tool_rules`: `shell ls` runs from then on, `shell
  rm` still asks); `/rules` lists and drops them. Every run is appended to `results/tools/<date>.jsonl`.
- **What shows.** One dim `→ search "rtx 4050 vram" · 1.4s · 3 results` line per call; while it runs the hood
  reads `→ search … · 3s`; the stats line counts the calls. Tab, or a click, opens the line to what came back
  (search and link results as cards in the window). Esc / Ctrl-C while a tool runs or asks stops the turn.
- **Adding one.** A function with `@tool(name, desc, {"arg": ("what", required)}, cap=, policy=, summary=)` in
  a module imported by `tools/__init__.py`; it returns a string.

The belt: **web.py** — `search` (DuckDuckGo HTML; Brave with `BRAVE_API_KEY` in the environment or `"keys"`
in the settings; Bing as the fallback), `fetch` (any page as readable text, article-aware, in 5000-character
parts with `start=`, `find=` for the passages around a word, pages cached ten minutes), `links`, `wiki`,
`http` (raw requests for APIs), `download`, `weather`. **browser.py** — Edge or Chrome headless over the
DevTools protocol with a standard-library websocket: `browse` (JavaScript runs), `click`, `type`, `scroll`,
`screenshot`, `browse_links`; one tab kept open; `LOKI_BROWSER` points at the executable if it is not found.
**system.py** — `sysinfo`, `processes` (cpu sampled live), `load` (what is turning the fans over: cpu by
process, gpu via nvidia-smi, thermal zones and fans where the firmware reports them), `proc` (path, command
line, parent chain, children, services, ports), `ports`, `services`, `events`, `gpu`, `kill`, `find`, `grep`;
Windows through PowerShell, Linux through /proc. **local.py** — `clock`, `calc`, `clipboard`, `notes` (the
model's own notebook, `results/notes.md`), `files`, `write`, `shell`, `python`, `studio` (queues a picture or
a video for the 4K agent).

## Studio (`studio/`)

The queue is `results/studio/queue.json`, shared by the window's studio tab, the model's `studio` tool and
`studio/runner.py`, which runs inside `app.py` (or alone: `python3 loki/studio/runner.py`) and hands jobs one
at a time to an agent process over three lines: `JOB <json>` in; `PROG <0-100> [note]`, `DONE <path>`, `FAIL
<reason>` out. `stub_agent.py` is the agent until the 4K model is tied in: it reports progress for a few
seconds and writes a placeholder PNG at the requested aspect. The real model is one setting,
`"studio_agent": ["python", "path/to/agent.py"]`, and that protocol. The tab shows progress as a hairline on
the frame, the finished render, and a strip of renders; files are served at `/out/<name>`.

## Protocols

**Engine** (the engine side is `patch_chat_mode.py`, already in the build): stdin, one command per line —
`U <think_budget> <answer_budget> <escaped templated text>`, `R` (clear the KV cache), `Q` (save memories and
exit), `X` (stop the turn). stdout — `READY <ctx>`, `T <id> <piece>`, `F <id> <piece>` (forced think-close
tokens), `END <eos|cap|full|stop> <think_n> <answer_n> <secs> <pos> <ctx>`, `RESET`, `FULL`. Think close is
token 128799, end of sentence 1. Escaping: `\n` for newline, `\\` for backslash. Do not change it without
changing `patch_chat_mode.py` in step; the engine is only built on the laptop.

**Window.** `GET /events` streams deltas: every top-level field plus the log from the first changed entry
(`log_from`, `log`); a new client gets one full snapshot. `POST /send {text}`, `/stop`, `/new`, `/open {id}`,
`/delete {id}`, `/tool {answer}`, `/studio {job}|{drop}`; `GET /state`, `/conversations`, `/studio`,
`/out/<file>`. The server listens on 127.0.0.1 only and serves files from `web/` only.

## Checking it

`python3 loki/tests.py` runs twenty-seven headless tests over the replay with a 4096 context (about four
minutes): the hood is a TV (the thought shows while it generates, is gone when it ends, and Tab does not bring it back — the text is still kept); the hood shows four lines and opens; text fills rows without reflow;
Ctrl-C asks twice; Esc stops; the scroll hint and hairline; a tool turn; ask then deny; `a` remembers; tools
off at 256; `/new` and `/open`; the palette completes and runs; Enter mid-turn queues and sends; Up recalls
and the draft survives; word jumps and kill; wide characters keep the border; text flows evenly between
bursts; the hood closes on a curve; `/again` keeps a branch; `/edit` loads the message; presets; an `@file`
goes with the message and a missing one is said; `/find` then `/open`; the bell after a long answer; the
engine dying and `/restart`. They write only under `results/` and clean up. The replay (`--replay`, `--keys`, `--frames`, `--size`) is how any layout
change is checked: scripted keys, every changed screen written as plain rows.

## Only the laptop can close

The search parsers against the live sites; `system.py` and the headless browser on Windows; the Edge app
window; the arrival fade at 1 token/s; tool behaviour with the real model. And the engine-side wins: a
`</tool>` stop sequence (the client's own stop gets most of it), a cached KV prefix for the tool list, and the
longer context that makes the belt an everyday thing.
